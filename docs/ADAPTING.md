# Adapting Ullr to your own tools

Ullr ships with ten simulated tools and one reference Tools service. This guide says what to change to put a real backend behind the Gateway, and what each change must preserve. It describes the code as it is. Ullr is a research prototype, not a product: nothing here makes a deployment secure by itself.

The security argument has two halves. The Gateway decides and records. The backend refuses what the Gateway has not authorized, or at least refuses anyone who does not hold the Gateway's credential, and executes each authorized action at most once. A backend that skips its half breaks guarantees G1, G2 and G7 ([`THREAT_MODEL.md`](THREAT_MODEL.md) §8), whatever the Gateway does.

## 1. Declare the tool in four places

There is no plugin system: a tool is declared in code, in four places that must agree. A tool missing from any of them is refused (default deny).

| Place | What to add | Why it is in code |
|---|---|---|
| `src/ullr_ai/gateway/policy.py`, `TOOL_TIERS` | The tool's tier: `R0` read, `R1` reversible, `R2` irreversible | The policy file cannot reclassify a tool: a policy that states another tier fails to load. |
| `src/ullr_ai/gateway/schemas.py`, `TOOLS` | The resource identifier pattern (or none) and a strict schema for every argument | Canonicalization and the action hash depend on it. Values are rejected, never repaired. |
| The backend (here `src/ullr_ai/tools_service/executions.py`, `MUTATING_TOOLS` and `_apply`) | The effect | See section 4. |
| `src/ullr_ai/agent/tools.py` | The definition the model sees and the mapping from a tool call to an action | Only for the benchmark agent; another agent needs its own mapping. |

**Choosing the tier.** Classify by effect, not by name. A tool that can destroy data through a "reversible" path is R2: in the hidden set, H09 destroys a document through `update_document` (R1), which the reference policy allows without approval. That is a pre-registered weakness of tiering by tool ([`tasks/hidden/HIDDEN_SET.md`](../tasks/hidden/HIDDEN_SET.md)). When in doubt, use R2.

**Writing the schema.** Use opaque identifiers for resources and recipients (`contact_7`, not an e-mail address), decimal strings with a fixed number of fraction digits for amounts, and closed enumerations wherever possible. Free text is NFC, without control or invisible characters. Anything that admits two spellings of the same action lets an approval for one spelling be argued to cover the other.

## 2. Write the policy

`policies/default.yaml` lists every tool, its tier (which must match `TOOL_TIERS`), optional constraints and budgets, and `default: deny`. Its SHA-256 is the policy hash, so any change, comments included, invalidates every outstanding approval.

- **Constraints** are checked before any approval: a proposal that violates them is denied and the approver never sees it. The reference policy has `max_amount` and a currency allow-list for refunds.
- **Budgets** are cumulative caps per key (`account_id`, `agent_id`) over a window, reserved inside the execution transaction. Use an account-level key for anything several agents can touch.
- **Tainted sessions.** `on_tainted_session` can escalate or deny when the session has read external content.
- **Approvals.** `ttl_seconds` and `max_pending_per_session`.

Constraints and budgets exist for refunds only. Another tool with numeric limits needs code in `policy.py` and `budget.py`: the policy format does not express arbitrary rules, on purpose.

## 3. Choose and provision the approver

R2 actions need a decision signed with Ed25519 by a key listed in the approver registry (`secrets/approvers.yaml`, generated by `make secrets`; one key, `human_1`). The Gateway takes the key from the registry, never from the decision.

- Generate the key where the approver works, and never give it to the agent container. Rotate it by changing the registry, which needs a Gateway restart.
- The approver needs the approver-channel token and a route to `gateway-approver`, on a network the agent cannot reach.
- `src/ullr_ai/approver/cli.py` lists pending requests, shows the action and the provenance derived by the Gateway, and signs. A real deployment needs a user interface over the same API. The three approvers in `src/ullr_ai/bench/approvers.py` are simulations for evaluation only. `AP-oracle` reads the task's ground truth: it is a control, not a model of a person.
- An approver can approve a harmful action. The system makes the decision informed (provenance, exact action) and bounded (one execution, one version, one expiry), not wise.

## 4. Adapt the backend: credential, idempotency, preconditions

The Gateway talks to the backend through `src/ullr_ai/gateway/executor_client.py`. A real backend must provide the same contract, directly or through a thin adapter that you trust as much as the backend:

| Route | Contract |
|---|---|
| `GET /v1/resources/{id}` | The resource's current `version` (an integer that changes on every mutation) and its `trust_label`, `internal` or `external`. |
| `POST /v1/execute` | Requires the executor token. For a mutation, requires `Idempotency-Key` and `If-Match` (the version the approval was bound to). Applies the effect and records the key in **one transaction**. A repeated key with the same request returns the first result without a second effect; a repeated key with a different request is refused. A stale `If-Match` is refused without effect. A read returns its result with `sources`, the trust label of everything it returned. |
| `GET /v1/executions/{key}` | What happened to a key. |
| `POST /v1/executions/{key}/resolve` | Definitive resolution for reconciliation: if the key was never executed, it is burned and any later request with it is refused. |

What this gives, and what it does not:

- **At most once (G7)** holds only if the backend enforces idempotency itself. If the real API has no idempotency keys, the adapter must hold them in the same transaction as the effect, which is impossible across a remote call that has its own side effects. Then G7 does not hold, and the documentation must say so.
- **Preconditions.** If the real API has no versions, the adapter cannot detect that the resource changed after approval. T5 is then not covered.
- **The backend is a credential barrier, not an authorization barrier.** The reference Tools service checks the token, the key and the precondition, but no approval, signature, amount or budget. Anyone holding the executor token can execute any schema-valid action. Everything rests on that token reaching only the Gateway (section 5). A backend that can verify the signed approval itself would remove this single point; Ullr does not implement it.

## 5. Isolate the network and hold the credentials

`docker/compose.yaml` is the reference topology. What matters is the property, not Docker:

- The agent can reach the Gateway's agent API and its model, and nothing else. In particular, not the backend, the approver channel, the admin API or the host.
- The executor token is given to the Gateway and the backend only. The approver key stays with the approver. The admin token stays with the orchestrator that issues sessions.
- Sessions are created by a trusted party (`POST /admin/sessions`) and the token is handed to the agent through a channel it cannot write. The agent API cannot create or switch sessions.
- Check the platform. The first L2 run found services of the Docker Desktop virtual machine reachable from the agent ([`results/l2/run-1/INVESTIGATION.md`](../results/l2/run-1/INVESTIGATION.md)). Run the L2 attacker (`make attack`) on your own platform before relying on the topology, and keep its positive controls.

The reference topology relies on Docker Desktop for macOS: `host.docker.internal` for the model relay, and `com.docker.network.bridge.inhibit_ipv4` on the agent networks. Docker Engine on Linux needs at least `extra_hosts` for the relay, and the isolation must be checked again there.

## 6. Audit, errors and retries

- **Audit.** Every security state transition writes its audit event in the same SQLite transaction; `verify-audit` checks the hash chain. Truncation of the tail is not detected, and nothing is anchored outside the host. For bypass measurement, cross-check the backend's execution log against the Gateway's actions, as `metrics.unbacked_executions` does: the audit log alone is not enough.
- **Errors fail closed.** A failure to write the audit, to reach the backend or to parse a reply means no execution. A timeout after the call leaves the action `UNKNOWN`, with its budget reserved, until reconciliation resolves the key. Reconciliation runs periodically and at start-up.
- **Retries.** An agent that retries after an unknown outcome creates a new proposal and needs a new approval: an approval is never reused. Your backend must not apply an effect from a burned key.

## 7. Limits that carry over

- Provenance is per session. It over-taints (the cost measured in L3: legitimate refunds rejected by `AP-provenance`) and does not follow content through written resources: a tainted session can write a document that a clean session later reads as internal (storage laundering; a fix is designed and deferred).
- Permitted reads disclose what they return. Ullr does not control exfiltration through allowed actions or their arguments, beyond what the policy and the approver see.
- Agent containers that share a network can talk to each other outside the Gateway's view.
- Revocation bounds authorization, not effects already authorized.
- The evaluation covers one model, one platform and simulated approvers. Adapting the tools invalidates every measured number: run L1, L2 and your own task suite again.
